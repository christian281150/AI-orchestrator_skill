# Phase 3 - Workspace setup

Everything the build depends on, set up once and proven by `preflight` before round 1. Order matters:
some steps (line endings, identity, secrets) are cheap now and very expensive to fix after the first
commit, hash or data load.

## 1. Folder layout (decide it, write it into START-HERE.md section 3)

| What | Where | Why |
|---|---|---|
| The repository | e.g. `~/src/<app>` or `E:\src\<app>` | one repo = one project; never work in an older version's repo |
| Lane worktrees | sibling folder `../<app>-wt/` | each lane has its own working copy; nothing shares a working tree |
| Run state, logs, fallback markers | `~/.agent-build/<app>/` (outside the repo) | never committed, never swept into a commit |
| Data (real, licensed, captures) | outside the repo, e.g. `~/data/<app>/` | never committed, never a test fixture, never sent to an AI provider |
| Owner's helper scripts, scratch | outside the repo, e.g. `~/src/<app>-tools/` | tools that operate on the repo shouldn't live in it |

## 2. Repository and git - before the first real commit
1. `git init -b main` (or clone the empty GitHub repo).
2. Run the kit: `python <skill>/kit/tools/orch.py init <repo> --name <app> --author-name "<name>" --author-email "<email>"`.
   It copies templates + tools, never overwrites, sets `core.hooksPath=.githooks` and the git author.
3. **`.gitattributes` first** (the kit writes it): fix line endings before anything is hashed. A file hashed
   under one setting and checked under another fails its checksum with unchanged content.
4. `.gitignore` covers secrets, captures (`*.har`), data, run state.
5. Hooks active: `pre-commit` (forbidden paths, secrets in added lines, board consistency, author) and
   `commit-msg` (forbidden trailer lines). Prove them: stage a fake `.har` -> commit must fail.
6. GitHub: private repo, branch protection on `main` if more than one human pushes. Push rights for the
   supervisor only if `push_after_round = true`.

## 3. Identity and credentials
- One git author for all commits (the owner's), set by init; the hook checks it.
- **Credentials as user-scope environment variables**, read by scripts, never printed, never in chat:
  - Windows: `[Environment]::SetEnvironmentVariable('NAME', '<value>', 'User')` typed by the owner in their
    own PowerShell (not pasted into a chat), then open a new terminal.
  - macOS/Linux: the shell profile, or better the keychain / `pass`, exported by a wrapper.
- One variable per identity, named for the identity (`DB_PASSWORD_APP`, `DB_PASSWORD_ADMIN`) - the admin
  identity and the app identity are different operators; whichever you connect as is stamped on every row.
- List the names in `orchestration.toml [safety].required_env` (preflight checks presence, never values).
- Build-only providers get credentials removed: `[providers.x].strip_env`. Note the residual risk: values
  may still be readable elsewhere on the machine (registry, keychain) - say so, don't pretend otherwise.
- Generated secrets are generated on the owner's machine and written straight to the environment.

## 4. Tools (check versions, write them into START-HERE)
- git, Python 3.11+ (the kit is stdlib only), the app's stack (Node, etc.).
- The provider CLIs chosen in Round 1: e.g. `claude`, `codex`, `gemini`. Log in to each once, interactively.
- Verify every command in `orchestration.toml` against `<cli> --help` for the installed version.
- Windows: know which `python` is first on PATH. A missing module can print an error and exit 0 (the Store
  stub does) - preflight and tests must use the exact interpreter (`.venv\Scripts\python.exe`).
- Skills: install what `SKILLS-PLAN.md` lists, for every engine that runs the role (Claude reads
  `.claude/skills` / `~/.claude/skills`; other engines their own folders, e.g. `.agents/skills`). Keep one
  source folder + an install script so copies never drift; pin versions. `orch.py skills` shows the inventory
  and what agent files name but lack; preflight fails on a missing one.

## 5. Test environment
- Local, synthetic test data, generated by a script in the repo. Live is never a fixture.
- Test database on its **own port** (e.g. 55432), never the general local one (5432) - a test that reaches
  the wrong server by default is a production incident waiting for a typo. Tests default to the test port;
  a guard test fails if any test defaults elsewhere.
- Local vs live version parity: write down both versions; say when a difference matters.
- A strict mode where "infrastructure unavailable" is a FAIL, not a skip, required before any verified claim.

## 6. The claude.ai Project (the memory the owner and every chat session share)
Create a Project for the app. Its instructions (copy and fill):

```
## What this is
<one paragraph: the app, who uses it, owner, technical level of the owner>

## First action, every session, no exceptions
1. Read the newest claude/HANDOVER-* doc.
2. Measure, don't trust: the repository is the source of truth - docs/coordination/PROGRESS.md (board)
   and docs/coordination/decisions-log.md (newest first). Project docs older than the newest handover
   contain status lines that are now false; the repo wins.

## How the build runs
<execution home, supervisor, providers and roles, max lanes, merge gate, never kill a running coordinator,
side sessions commit only via safe-commit>

## Which session are you?
Interactive: short, action first. Autonomous: two legal turn endings only. Monitoring: adjust, don't build.

## Standing rules - the owner's words
<decide-and-log; never twice; branches; money; credentials never in chat; evidence; reserved actions>

## Where things are
<paths, server names only if the Project is private, database project id, run-state dir>
```
Project docs: `START-HERE`, the spec, architecture, `SCOPE`, newest handover. Status lives in the repo, not
in Project docs.

## 7. Scheduling (unattended only)
- Supervisor at logon, restart on failure: `tools/scheduling/` has Windows Task Scheduler, launchd and
  systemd templates.
- The PC must not sleep while plugged in (Windows power settings; macOS `caffeinate`), or rounds pause.
- Dashboard: a claude.ai scheduled task, twice a day, that runs `orch.py snapshot` on the machine and writes
  the snapshot into the dashboard artifact's database. If the data is on the PC, the task needs "require this
  computer" turned on in the desktop app.
- Remote tool calls time out (~60 s): long jobs start detached and are polled.

## 8. Prove it
`python tools/orch.py preflight` -> every line PASS (WARN explained). Paste the verbatim summary into the
first handover. Then one dry round with a trivial P1 item before the real queue.
